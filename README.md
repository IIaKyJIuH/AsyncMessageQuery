# Async MessageQuery

Backend-сервис для асинхронной обработки задач на async-FastAPI + RabbitMQ + PostgreSQL.

Архитектуру старался делать интуитивно понятной, не считаю, что нужно оставлять как можно больше комментариев в коде, это говорит о костылях и допущениях, в то время как код должен читаться as-is.

## Быстрый старт (Docker)

```bash
docker-compose up --build
```

Кидать запросы будем на `http://localhost:8000`.

### Пример запроса

```bash
curl -X POST http://localhost:8000/tasks \
  -H "Content-Type: application/json" \
  -d '{"payload": "hello"}'
```

Ответ:

```json
{"id": "<task_id>"}
```

Проверка статуса (как будто вы ожидали этого):

```bash
curl http://localhost:8000/tasks/<task_id>
```

Ответ:

```json
{
    "id": "<task_id>",
    "payload": "<payload>",
    "status": "<TaskStatus>",
    "result": "<result>",
    "created_at": "<isodatetime>",
    "updated_at": "<isodatetime>"
}
```

## Поведение

### В приложении

Как проходит обработка:
- API принимает задачу и сохраняет её в БД со статусом `PENDING`.
- Затем задача отправляется в очередь RabbitMQ.

### В воркере

- Воркер забирает сообщение из очереди, ставит статус `PROCESSING`, ждёт 2–5 секунд, имитируя работу, и пишет результат.
- Если всё прошло нормально — статус `DONE`. Если что-то сломалось — `FAILED` (ошибку по обычному рандому сделал).

## Локальная разработка

Требования: Python 3.13, uv.

```bash
uv venv
uv sync --dev
uv run uvicorn app.main:app --reload
```

В отдельном терминале запускаем обработчик, тасок от брокера

```bash
uv run python -m app.worker
```


## Примечания к проекту

- Для Docker используется отдельный файл окружения `.env.docker` (с хостами `postgres` и `rabbitmq`). Для локального запуска — `.env` (`localhost`). Пример всех использующихся полей есть в `.env.example`, ну ещё в `app/config.py::Settings`

- `app/main.py` - эндпоинты fastapi, `app/worker.py` - обработчик для сообщений от брокера, `mq/rabbit_broker.py` - там логика работы с RabbitMQ, остальное интуитивно понятно и даже примитивно.

## Почему RabbitMQ

Потому что она во всех смыслах подходит для таких "мини-проектов". Поднять легко, вкурить суть легко, асинхронная механика "отдал -> воркер забрал” работает и гарантировано доставляет сообщения с задачами получателям. К тому же тут не требуется стриминг в реальном времени на первый взгляд.

## Масштабирование решения

- Вместо docker-compose перейти на оркестратор (k8s) для распределённой нагрузки, масштабирования и увеличения отказоустойчивости.
- При увеличении количества задач банально поднимать больше воркеров. Очередь сообщений раскидает задачи сама.
- Если нужен будет непрерывный стриминг + хранение истории + огромная скорость обрабобтки -> однозначно переход на Kafka.
- Использовать отдельные очереди (мб с отдельным роутингом) для разных типов задач.
- шардирование/репликация БД для снижения нагрузки.
- Добавить метрики(prometheus)/алерты для оперативного выявления потенциально слабых мест.

## Потенциальные точки отказа

- RabbitMQ без кластера/репликации => при перегрузе задачи не будут доставляться.
- PostgreSQL в одиночном экземпляре без репликации => при перегрузе таски будут теряться.
- Отсутствие ретраев на публикацию задач, централизованного мониторинга и алертов => при факапах типа "проблем нет" в моменте.
